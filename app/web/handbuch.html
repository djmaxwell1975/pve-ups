PVE-UPS — Benutzerhandbuch

Eine schlanke USV-Shutdown-Appliance für Proxmox VE und Proxmox Backup Server: Sie überwacht eine oder mehrere USVs — per SNMP oder über einen NUT-Server — und fährt bei Stromausfall die zugeordneten Abschaltziele geordnet herunter, ohne irgendwo von Hand gepflegte Konfigurationsdateien. Dieses Handbuch richtet sich an technisch versierte Administratoren, die das Produkt noch nicht kennen.

1 Was ist PVE-UPS?

PVE-UPS ersetzt klassische, herstellergebundene USV-Shutdown-Appliances (wie APC PowerChute Network Shutdown) für Proxmox-Umgebungen. Die Software läuft als ein einzelner, ressourcenschonender unprivileged LXC (~256 MB RAM) und benötigt nur ein Installer-Skript.

Kernfunktionen

  • Überwachung einer oder mehrerer USVs — mit SNMP-Netzwerkkarte (Standard RFC 1628 oder Hersteller-MIB wie APC PowerNet, SNMP v1/v2c/v3, reine Python-Implementierung) oder über einen NUT-Server, worüber USB- und seriell angeschlossene USVs gelesen werden.
  • Geordneter Shutdown über ein Proxmox-VE- oder PBS-API-Token (jeweiliges Power-Recht) — kein Root-SSH nötig.
  • Host↔USV-Zuordnung mit Logik pro Host (UND/ODER) für redundante Netzteile bzw. aufgeteilte Last, inkl. Schaubild im Webinterface.
  • Komplette Einrichtung über einen Web-Wizard mit Test-Buttons.
  • Weboberfläche auf Englisch und Deutsch — automatisch passend zur Browsersprache.
  • Fail-safe: ein Kontaktverlust zur USV löst standardmäßig nur Alarm aus, keinen Shutdown.
  • Dry-Run-Modus für eine gefahrlose Inbetriebnahme.
  • Lesender REST/JSON-Status für Monitoring (/api/status, /api/health).

2 Voraussetzungen

  • Ein Proxmox VE-Host (Standalone — kein Cluster-/HA-Manager-Eingriff), auf dem der LXC laufen kann. Typischerweise einer der zu schützenden Hosts.
  • Eine oder mehrere USVs, auf eine von zwei Arten erreichbar:
    • mit SNMP-Netzwerkkarte, die die Standard-RFC-1628-UPS-MIB (herstellerunabhängig) oder eine unterstützte Hersteller-MIB bereitstellt — APC PowerNet, womit auch APC-Karten ohne RFC 1628 erfasst sind (siehe Abschnitt 5), oder
    • per USB- oder seriellem Kabel an einer Maschine, auf der ein NUT-Server (upsd) läuft — siehe Abschnitt 5.
  • Netzwerkverbindung zwischen Appliance und USV-Quelle (Lesezugriff genügt: UDP 161 bei SNMP, TCP 3493 bei NUT) sowie zu den APIs der Abschaltziele (HTTPS, normalerweise Port 8006 bei PVE und 8007 bei PBS).

3 Installation & Einrichtung

Die Installation erfolgt direkt aus der Proxmox-Node-Shell (Webinterface → Node → >_ Shell, als root). Das Skript lädt das aktuelle Release-Paket von GitHub nach, entpackt es und legt den LXC an:

bash -c "$(curl -fsSL https://github.com/ffind-dev/pve-ups/releases/latest/download/install.sh)"
# z.B. mit fester IP:
curl -fsSL https://github.com/ffind-dev/pve-ups/releases/latest/download/install.sh | bash -s -- \
  --ctid 950 --ip 10.0.0.50/24 --gateway 10.0.0.1 --hostname pve-usv

Anschließend das Webinterface unter http://<container-ip>:8080 öffnen und den Wizard durchlaufen:

  1. UI-Passwort setzen.
  2. USVs anlegen (Quelle, Adresse, Zugangsdaten — siehe Abschnitt 5) und je USV mit „USV testen" prüfen.
  3. Abschaltziele eintragen (API-Token, siehe Abschnitt 4) und „Verbindung testen". Festlegen, welche USVs einen Host versorgen und nach welcher Logik (UND/ODER).
  4. Schwellwerte setzen bzw. die Standardwerte übernehmen.
  5. Optional den Benachrichtigungs-Webhook einrichten (HTTP-POST an ein Ticket-/Chat-/Monitoring-System).
Solange der Dry-Run aktiv ist, wird nichts heruntergefahren — ideal zum Testen. Erst wenn alles passt, den Dry-Run deaktivieren (Modus „SCHARF").
Läuft der LXC auf einem der geschützten Hosts, diesen in der Host-Liste als „Dieser Host" markieren — er wird dann garantiert zuletzt heruntergefahren.

4 API-Token für Abschaltziele anlegen

Für jedes Ziel einmalig einen dedizierten Benutzer und API-Token mit ausschließlich dem nötigen Power-Recht erzeugen. Für Proxmox VE:

pveum user add ups@pve
pveum role add UpsShutdown -privs "Sys.PowerMgmt"
pveum acl modify /nodes -user ups@pve -role UpsShutdown
pveum user token add ups@pve shutdown --privsep 0

Der letzte Befehl gibt Token-ID (ups@pve!shutdown) und Secret aus. Beides bei Plattform „Proxmox VE“ im Wizard eintragen (API-URL https://<host-ip>:8006) und mit „Test“ prüfen. Das Token ist jederzeit widerrufbar und ersetzt einen Root-SSH-Zugang.

Proxmox Backup Server

Einen dedizierten PBS-Benutzer und API-Token anlegen und dem Token ausschließlich Sys.PowerManagement auf /system/status geben. PBS verwendet normalerweise https://<host-ip>:8007 und den API-Node-Namen localhost. Im Wizard die Plattform „Proxmox Backup Server“ wählen und localhost, URL, Token-ID und Secret eintragen. Die Token-ID hat weiterhin die Form benutzer@realm!tokenname, aber PBS verlangt zur Authentisierung PBSAPIToken=TOKENID:TOKENSECRET; PVE-UPS wählt dieses Format automatisch.

Mit der Abschaltreihenfolge Workload-Hosts vor PBS und PBS vor der Appliance einordnen. Der aktuelle Client sendet den geordneten Shutdown-Befehl, prüft aber noch keine laufenden Backup-Jobs und leert keine Queue.

5 USV-Quellen

Jeder USV-Eintrag im Wizard hat eine Auswahl „Gelesen über". Beide Quellen lassen sich in einer Instanz frei mischen, und alles Weitere — Schwellwerte, Host-Zuordnung, Fail-safe-Regeln — ist für beide identisch.

SNMP (USV mit Netzwerkkarte)

In der Weboberfläche der USV-Netzwerkkarte (meist unter Network → SNMPv1 bzw. SNMPv3) den Zugriff aktivieren und der Appliance-IP Lesezugriff geben. Es wird nie etwas geschrieben. Standardport 161/UDP.

Welche MIB gelesen wird

Jede SNMP-USV hat eine Einstellung MIB. Sie entscheidet, welcher Satz an Objekten abgefragt wird — die Werte selbst, die Schwellwerte und alles Weitere sind in beiden Fällen dieselben.

  • Automatisch (Standard und für nahezu jedes Gerät die richtige Antwort): Es wird der Standard RFC 1628 gelesen und auf eine Hersteller-MIB gewechselt, sobald die USV darauf antwortet. Die Erkennung kostet keine zusätzliche Abfrage, und ein späteres Firmware-Update, das RFC 1628 nachrüstet, wird von selbst übernommen.
  • RFC 1628 (Standard): die herstellerunabhängige UPS-MIB, sonst nichts.
  • APC PowerNet: die MIB der Netzwerkkarten von APC/Schneider.

Besonders bei APC ist eine Hersteller-MIB nötig: Schneider unterstützt RFC 1628 nur auf der Network Management Card 2 (AP9630/AP9631/AP9635) ab Firmware sumx/sy v5.1.7; die älteren NMC1-Karten (AP9617/AP9618/AP9619) sprechen ausschließlich PowerNet und sind über den Standard gar nicht lesbar. Auch auf Karten, die beides beherrschen, ist PowerNet die bessere Quelle: Sie liefert die Restlaufzeit in Hundertstelsekunden statt in ganzen Minuten und meldet einen Selbsttest als eigenen Zustand — RFC 1628 kann einen Selbsttest nicht von einem echten Stromausfall unterscheiden.

Eine MIB fest wählen nur, um sie zu erzwingen, etwa um ein Gerät zum Vergleich auf den Standard festzunageln.

NUT-Server (USB- und serielle USVs)

Eine USV ohne Netzwerkkarte wird über Network UPS Tools erreicht: Auf der Maschine, an der die USV steckt, läuft upsd, und PVE-UPS liest von dort über TCP 3493. Häufig existiert so ein Server bereits — Synology- und QNAP-NAS haben eine „USV-Server"-Option, ebenso TrueNAS und OPNsense; sonst genügt ein Raspberry Pi oder ein Proxmox-Host mit dem Paket nut-server.

Nötig sind drei Angaben: der Host, auf dem upsd läuft, der USV-Name wie in dessen ups.conf konfiguriert (upsc -l <host> listet die verfügbaren Namen) und optional Benutzer und Passwort — ein Standard-upsd erlaubt das Lesen von Variablen auch ohne beides.

PVE-UPS ist ein strikt nur lesender NUT-Client: Es fragt ausschließlich die Variablenliste ab, sendet nie einen Befehl und betreibt kein upsmon. NUT dient als Gerätetreiber; Schwellwerte, Host-Logik und die Shutdown-Entscheidung bleiben in dieser Appliance. Auf den geschützten Hosts ist nichts einzurichten.
Das NUT-Protokoll ist unverschlüsselt und gehört in ein vertrauenswürdiges Netz. Läuft upsd auf einer Maschine, die PVE-UPS selbst herunterfährt, sollte genau dieser Host als „Dieser Host" markiert sein oder die höchste Shutdown-Reihenfolge haben — sonst verschwindet die Datenquelle mitten im Ausfall. Der Akkubetrieb-Countdown läuft in dem Fall zwar weiter (siehe Abschnitt 7), eine weiterhin erreichbare Quelle ist aber besser.

Testergebnis lesen

Unter der Ergebniszeile bietet „USV testen" die Details je Objekt — jedes Objekt einzeln abgefragt, mit seinem Wert oder dem Grund, warum es fehlt. Der Block klappt von selbst auf, sobald etwas nicht stimmt, und trennt damit die Fälle, die sonst gleich aussehen:

  • Nichts antwortet (jede Zeile ein Fehler): Adresse, Port oder Zugangsdaten stimmen nicht, oder eine Firewall blockiert UDP 161 (SNMP) bzw. TCP 3493 (NUT). Bei NUT zusätzlich prüfen, ob die LISTEN-Direktive von upsd diesen Host überhaupt umfasst — standardmäßig lauscht er nur auf localhost.
  • Manche Objekte antworten, andere melden noSuchObject / noSuchInstance (SNMP) bzw. „von diesem Treiber nicht geliefert" (NUT): Das Gerät veröffentlicht diese Werte schlicht nicht. Sobald das einen Auslöser betrifft, sagt der Test das im Klartext über der Tabelle — ein Treiber ohne battery.runtime macht etwa die Schwelle „Restlaufzeit unter (min)" dauerhaft wirkungslos. Stattdessen den Zeitgeber „Akkubetrieb länger als (s)" nutzen: Er läuft auf der eigenen Uhr der Appliance und funktioniert immer.
  • noSuchName unter SNMPv1: Das Objekt fehlt und v1 bricht eine Sammelabfrage ab, sobald ein Objekt fehlt — die reguläre Abfrage scheitert dann komplett, obwohl die übrigen Werte lesbar wären. Die USV nach Möglichkeit auf v2c umstellen.
  • Alle RFC-1628-Objekte fehlen, alle Hersteller-Objekte antworten: normal bei einer APC-Karte ohne RFC-1628-Unterstützung. Im Modus Automatisch werden beide MIBs aufgelistet, die tatsächlich genutzte steht oben, und die Zeile über der Tabelle nennt sie. Es ist nichts zu ändern — die gezählten Objekte und die Hinweise zu Auslösern beziehen sich immer auf die genutzte MIB, nicht auf die unterlegene.
  • „veraltete Daten" (NUT): upsd antwortet, aber sein Treiber hat den Kontakt zur USV verloren. Die noch gelieferten Werte sind alt, deshalb gilt die USV als nicht erreichbar — Alarm, nie ein Shutdown. Den NUT-Treiber auf der Maschine neu starten.

6 Funktion & Logik

Die Engine fragt alle USVs parallel ab und wertet jede USV unabhängig aus. Pro USV gibt es eine einfache Zustandsabfolge:

ONLINE Netzbetrieb  →  ON_BATTERY Stromausfall, USV im Akku  →  ausgelöst sobald eine Schwelle greift

Welcher Host fährt herunter?

Das entscheidet die Zuordnung jedes Hosts zu seinen USVs und seine Logik:

  • UND (ups_policy = all, Standard): Der Host fährt erst herunter, wenn alle ihm zugeordneten USVs ausgelöst haben — exakt das Verhalten für Server mit redundanten Netzteilen (je Netzteil eine USV). Solange eine USV noch Strom liefert, bleibt der Host an.
  • ODER (ups_policy = any): Der Host fährt herunter, sobald eine zugeordnete USV auslöst — für aufgeteilte, nicht redundante Last.

Mehrere fällige Hosts werden geordnet abgeschaltet. Der Host, der die Appliance selbst trägt (this_host), kommt zuletzt dran, damit er die übrigen noch abschalten kann. Tipp: den Appliance-Host an alle USVs hängen, damit er zuverlässig zuletzt fällig wird.

Erholt sich eine erforderliche USV (Netz kehrt zurück), wird ein noch nicht ausgeführter Shutdown wieder abgebrochen und der Zustand zurückgesetzt.

7 Fail-safe & Sonderfälle

Grundprinzip: Ein Kontaktverlust zur USV ist kein bestätigter Stromausfall — die USV antwortet vielleicht nur kurz nicht, oder ein Switch dazwischen ist weg. Standardmäßig löst ein Kommunikationsverlust daher nur Alarm aus, keinen Shutdown. Zwei optionale Einstellungen verfeinern das:

  • Shutdown bei Verlust fortsetzen (Standard an): Reißt der Kontakt ab, nachdem bereits ein Akkubetrieb bestätigt war, läuft ein gestarteter Akkubetrieb-Countdown auf der lokalen Uhr weiter und löst bei Ablauf aus. Nur dieser zeitbasierte Auslöser überlebt den „blinden" Zustand (Restlaufzeit und Ladestand sind dann nicht lesbar). Hatte ein Auslöser (z. B. Battery-Low oder Ladestand-Schwelle) dagegen schon vor dem Verbindungsabriss gegriffen, bleibt er bestehen und wird nicht auf den Zeitcountdown zurückgestuft. Countdown und ausgelöster Zustand überleben auch einen Neustart des Dienstes: beides wird auf Platte gemerkt und beim Start wiederhergestellt (max. 24 h alt).
  • Shutdown nach X Minuten reinem Verlust (Standard aus): Behandelt einen reinen Kommunikationsverlust (ohne vorher bestätigten Akkubetrieb) nach X Minuten doch als Ausfall. Bewusstes Opt-in für Umgebungen, in denen ein längerer Kontaktverlust als kritisch gilt.

Übersicht der Fälle

SituationVerhalten

8 Auslöser & Schwellen

Es genügt eine zutreffende Bedingung. Alle Werte sind im Wizard änderbar (Feld leeren = Bedingung aus); Schwellen lassen sich global setzen und pro USV überschreiben.

BedingungStandard
Akkubetrieb länger als600 s
Restlaufzeit unter10 min
Ladestand unter30 %
USV meldet battery low/depletedan

Poll-Intervall: 30 s im Netzbetrieb, 8 s im Akkubetrieb.

Battery-Low, Restlaufzeit- und Ladestand-Schwelle lösen sofort aus — unabhängig vom Zeit-Countdown. Der im Dashboard angezeigte Countdown betrifft ausschließlich die Bedingung „Akkubetrieb länger als" und verschwindet, sobald die USV ausgelöst hat. Ob ein Host daraufhin sofort herunterfährt, entscheidet seine UND-/ODER-Logik (siehe Funktion & Logik): bei UND wartet er, bis alle ihn versorgenden USVs ausgelöst haben.

9 Monitoring / REST

Zwei lesende Endpunkte stehen ohne Authentifizierung und ohne Secrets zur Verfügung:

  • GET /api/status — kompletter Zustand: Appliance, alle USVs, Hosts, Shutdown-Status sowie die Ereignisse der letzten 48 h inkl. Severity-Zusammenfassung.
  • GET /api/health — 200, wenn die Engine läuft (mit Version und Erreichbarkeit der USVs), sonst 503. Ideal für Uptime-Checks.
curl http://<container-ip>:8080/api/status | jq
# nur kritische Ereignisse der letzten 48 h:
curl -s http://<container-ip>:8080/api/status \
  | jq '.events[] | select(.severity=="critical")'

Alle ändernden Endpunkte (Wizard speichern, Test-Shutdown) sind passwortgeschützt.

Ereignisprotokoll, Webhook-Nachrichten und API-Meldungen sind einheitlich englisch — unabhängig von der gewählten Oberflächensprache. Das hält Auswertung und Monitoring über Installationen hinweg konsistent.

10 Updates & Betrieb

Updates lassen sich direkt im Webinterface hochladen; ein schmaler, privilegierter Begleitdienst wendet sie an (die App selbst bleibt unprivilegiert). Nach dem Upload wird das Update typischerweise innerhalb weniger Sekunden eingespielt. Über das Webinterface können zudem Konfiguration exportiert/importiert, NTP-Server und Zeitzone gesetzt und das Ereignisprotokoll eingesehen/geleert werden.

Hinweis: Die Zeitzone (Abschnitt System, z.B. Europe/Berlin) sollte gesetzt werden, da der Container sonst in UTC läuft. Die Selbsttest-Startzeit gilt in dieser lokalen Zeit; nach dem Setzen der Zeitzone startet der Dienst kurz neu.

Selbsttest der Abschaltziel-Verbindungen

Die Appliance prüft selbstständig je Ziel, ob API-Token und Power-Recht noch funktionieren — damit abgelaufene oder zurückgezogene Zugangsdaten lange vor dem Ernstfall auffallen. Gesteuert wird das über zwei Einstellungen im Abschnitt System: eine Startzeit (volle Stunde) und ein Intervall von 15 Minuten bis 24 Stunden. Beide zusammen ergeben feste Tageszeiten: Startzeit 09:00 mit 6-Stunden-Intervall bedeutet 09:00, 15:00, 21:00 und 03:00. Standard ist täglich.

Ein fehlgeschlagener Selbsttest wird immer protokolliert und benachrichtigt. Ein erfolgreicher landet höchstens einmal täglich im Ereignisprotokoll (sowie bei Erholung nach einem Fehler), damit ein kurzes Intervall das Protokoll nicht zuschüttet. Im Akkubetrieb wird der Selbsttest komplett ausgelassen — im Ernstfall hat der Countdown Vorrang. Ein Neustart wiederholt einen Selbsttest nicht, der im aktuellen Zeitfenster bereits gelaufen ist.

Update von Version 2.x auf 3.x

Das jeweils aktuelle Release-Paket (pve-usv-<version>.tar.gz) von der GitHub-Release-Seite herunterladen und im Webinterface unter „Update" hochladen — die Konfiguration bleibt vollständig erhalten. Zwei Verhaltensänderungen: die E-Mail-Benachrichtigung entfällt (ein evtl. konfigurierter SMTP-Eintrag wird beim nächsten Speichern automatisch entfernt; der Webhook bleibt), und Ereignis-/ Webhook-Texte sind ab 3.0.0 englisch.

Docker-Bereitstellung

Als Alternative zur LXC-Installation wird bei jedem Release zusätzlich ein fertiges Image nach ghcr.io/ffind-dev/pve-ups veröffentlicht. Eine fertige docker-compose.example.yml liegt im Repository; das Wesentliche daraus:

services:
  pve-ups:
    image: ghcr.io/ffind-dev/pve-ups:latest
    container_name: pve-ups
    restart: unless-stopped
    ports: ["8080:8080"]
    environment:
      - TZ=Europe/Berlin
    volumes:
      - pve-ups-config:/etc/pve-usv    # config.yaml (Secrets, 0600)
      - pve-ups-data:/var/lib/pve-usv  # events.db + Engine-Zustand
volumes:
  pve-ups-config:
  pve-ups-data:

Anschließend http://<docker-host>:8080 öffnen und denselben Wizard wie beim LXC durchlaufen. Konfiguration und Eventlog bleiben über die beiden eingebundenen Volumes erhalten, ein docker compose down verliert also nichts.

Da es im Image keinen privilegierten Begleitprozess (kein systemd) gibt, funktionieren dort zwei Dinge anders: Updates erfolgen durch ein neues Image-Tag und ein Neuerstellen des Containers (docker compose pull && docker compose up -d) statt über den In-App-Uploader, und NTP/Zeitzone liegen in der Verantwortung des Docker-Hosts/Orchestrators statt über den Wizard gesetzt zu werden — beide Bereiche sind im Webinterface ausgeblendet. Alles Weitere (USV-Abfrage, PVE/PBS-Shutdown, Schwellwerte, Webhook, Selbsttest) ist identisch.

TZ am Container setzen. Die Selbsttest-Startzeit gilt in der lokalen Zeit des Containers, und ohne TZ läuft der Container in UTC — im Docker-Modus lässt sich die Zeitzone nicht über das Webinterface setzen.
Liegt das eigene Netz innerhalb von 172.17.0.0/16 – 172.31.0.0/16, den Standard-Adresspool von Docker vor dem Start des Containers verschieben — Docker beansprucht diesen Bereich für seine Bridges, und der Container würde eine USV oder einen Proxmox-Host darin nicht mehr erreichen. In /etc/docker/daemon.json z.B. {"bip":"10.210.0.1/24","default-address-pools":[{"base":"10.211.0.0/16","size":24}]}, danach systemctl restart docker.

11 Fehlerbehebung

Update bleibt in der Warteschlange

Bleibt ein hochgeladenes Update bei „⏳ In Warteschlange" stehen, ist der Queue-Drainer auf dieser Instanz nicht aktiv. Das passiert einmalig bei Boxen, die aus einer sehr alten Version aktualisiert wurden. Einmalig im Container ausführen (aktiviert den Dienst dauerhaft):

pct exec <CTID> -- systemctl start pve-usv-agent.service
# oder direkt im Container:
systemctl start pve-usv-agent.service

USV nicht erreichbar / Alarm

Adresse, Zugangsdaten und die Firewall zwischen Appliance und USV-Quelle prüfen. Im Wizard zeigt „USV testen" die genaue Ursache — die Details je Objekt aufklappen, um zu sehen, welches Objekt warum scheitert (siehe USV-Quellen). Ein Kommunikationsverlust allein fährt nichts herunter (Fail-safe).

Eine Schwelle löst nie aus

Nicht jedes Gerät meldet jeden Wert. „USV testen" ausführen: Liefert das Gerät keine Restlaufzeit oder keinen Ladestand, sagt der Test das über der Objekttabelle — die zugehörige Schwelle ist dann dauerhaft wirkungslos. Stattdessen „Akkubetrieb länger als (s)" nutzen; dieser Zeitgeber läuft auf der eigenen Uhr der Appliance.

Bei einer SNMP-USV zusätzlich die Einstellung MIB prüfen. Viele Karten veröffentlichen über ihre Hersteller-MIB, was sie in RFC 1628 auslassen; Automatisch findet das von selbst, ein Blick lohnt also nur, wenn die MIB von Hand festgelegt wurde (siehe USV-Quellen).

Eine APC-USV funktioniert nicht / liefert nichts Brauchbares

Die Einstellung MIB auf Automatisch stehen lassen — die APC-PowerNet- MIB wird dann von selbst genutzt. Nötig ist sie, weil Schneider RFC 1628 nur auf der Network Management Card 2 (AP9630/AP9631/AP9635) ab Firmware sumx/sy v5.1.7 unterstützt, während die älteren NMC1-Karten (AP9617/AP9618/AP9619) sie gar nicht implementieren. „USV testen" zeigt, welche MIB genutzt wurde und welche Objekte jede von beiden beantwortet hat.

NUT: „kennt keine USV mit diesem Namen" oder gar keine Antwort

Der USV-Name muss dem Abschnittsnamen in der ups.conf von upsd entsprechen; upsc -l <host> listet die gültigen Namen. Antwortet gar nichts, lauscht upsd meist nur auf localhost — seine LISTEN-Direktive muss die Schnittstelle abdecken, über die die Appliance verbindet, und TCP 3493 muss offen sein.

SNMPv3 mit Verschlüsselung schlägt fehl

Meldet ein authPriv-Benutzer „Ciphering services not available" oder weist der Test auf fehlende Verschlüsselung hin, fehlt der Appliance das Python-Paket cryptography, das die DES-/AES-Verfahren bereitstellt. Versionen bis einschließlich 3.0.0 haben es nicht mitinstalliert. Ein Update der Appliance behebt das — das Paket kommt automatisch mit. Zwei Dinge sind gut zu wissen: Es betrifft jedes Verschlüsselungsverfahren, ein Wechsel von DES auf AES hilft also nicht, und authNoPriv (Authentifizierung MD5/SHA, Verschlüsselung „none") funktioniert in der Zwischenzeit weiter, weil die Authentifizierung diese Verfahren nicht braucht.

Interne Namen: pve-usv

Der Produktname ist PVE-UPS, technisch heißen Dienst und Pfade aber weiterhin pve-usv — also z. B. systemctl status pve-usv, /etc/pve-usv/config.yaml und /var/lib/pve-usv/. Das ist beabsichtigt und hält Updates bestehender Installationen kompatibel.

3.3.0 2026
  • APC-USVs werden richtig unterstützt: Eine SNMP-USV lässt sich jetzt über eine Hersteller-MIB statt über RFC 1628 lesen, als erste APC PowerNet. Damit sind auch APC-Karten erfasst, die über RFC 1628 gar nicht erreichbar sind — die älteren NMC1 (AP9617/AP9618/AP9619) — sowie NMC2-Karten mit Firmware unter sumx/sy v5.1.7. Siehe USV-Quellen.
  • Die neue Einstellung MIB steht auf Automatisch und erfordert keine Aufmerksamkeit: Bestehende USV-Einträge erhalten sie beim Update, und eine USV wechselt von selbst auf ihre Hersteller-MIB, sobald sie darauf antwortet.
  • Karten, die beides beherrschen, liefern genauere Werte: PowerNet meldet die Restlaufzeit in Hundertstelsekunden statt in ganzen Minuten und kennzeichnet einen Selbsttest als solchen — RFC 1628 kann ihn nicht von einem echten Stromausfall unterscheiden.
  • Der USV-Test erklärt sich selbst: Im Modus Automatisch listet er beide MIBs auf und nennt, für welche er sich entschieden hat und warum. Das Dashboard zeigt die genutzte MIB an.
3.2.0 2026
  • USVs ohne Netzwerkkarte lassen sich jetzt überwachen: Ein USV-Eintrag wird entweder wie bisher per SNMP gelesen oder über einen NUT-Server — so werden USB- und seriell angeschlossene USVs erreicht. Beides ist in einer Instanz mischbar. Siehe USV-Quellen.
  • PVE-UPS bleibt ein strikt nur lesender NUT-Client — kein upsmon, keine Shutdown-Skripte, keine Konfigdateien. Die Entscheidung bleibt in der Appliance.
  • Der USV-Test benennt tote Schwellen: Meldet ein Gerät weder Restlaufzeit noch Ladestand, sagt der Test das — statt eine Schwelle zu hinterlassen, die stillschweigend nie auslöst.
  • Ein NUT-Server, der veraltete Daten liefert (sein Treiber ist abgestürzt), gilt als nicht erreichbar — Alarm, nie ein Shutdown, und nie mit „Netzbetrieb" verwechselt.
3.1.0 2026
  • SNMPv3 mit Verschlüsselung funktioniert jetzt. Ein authPriv-Benutzer scheiterte bis einschließlich 3.0.0 mit „Ciphering services not available" — eine fehlende Abhängigkeit, die das Update automatisch mitinstalliert. Siehe Fehlerbehebung.
  • Docker-Bereitstellung als Alternative zum LXC: Bei jedem Release wird zusätzlich ein fertiges Image veröffentlicht. Siehe Docker-Bereitstellung.
  • SNMP-Test mit Details je Objekt: jedes RFC-1628-Objekt mit Wert oder dem Grund, warum es fehlt — falsche Zugangsdaten, blockierter Port und eine unvollständige USV sind damit auf einen Blick unterscheidbar.
  • Selbsttest mit Intervall: Aus der Uhrzeit wird eine Startzeit, dazu eine Wiederholung von 15 Minuten bis 24 Stunden. Bestehende Installationen behalten ihren täglichen Rhythmus.
3.0.0 2026
  • Erste öffentliche Veröffentlichung auf GitHub unter dem Namen PVE-UPS (Dienst-/Pfadnamen bleiben intern pve-usv).
  • Weboberfläche zweisprachig: Englisch (Standard) und Deutsch, automatisch passend zur Browsersprache; Benutzerhandbuch in beiden Sprachen.
  • Ereignisprotokoll, Webhook-Nachrichten und API-Meldungen einheitlich englisch.
  • E-Mail-Benachrichtigung entfernt — der Webhook deckt Benachrichtigungen ab; bestehende SMTP-Einträge werden beim Update automatisch verworfen.
  • Installation und Updates direkt über GitHub-Releases (Install-Einzeiler, Update per Paket-Upload im Webinterface; von 2.x nahtlos möglich).
